## Intent and scope

Provide an active pending or approved account a numeric SMS-code path for verifying
its own phone. This follows the phone-confirmation part of
`docs/RAUI_ACCOUNT_SCENARIO_2026_10_08.md`, bounded by the master execution plan,
technical specification, and registration-onboarding approval policy. Email/password
registration remains the entry point. Contact verification never grants registration
approval, changes roles, or reactivates an account.

Exclude anonymous phone signup/login, reset/recovery approval, calls/last-four-digit
verification, social/ESIA/Sber login, tariff/quota rules, provider callbacks, and
background retries. No real messages may be sent as implementation validation
without an explicitly authorized controlled-recipient test.

## Architecture and alternatives

Use a separate `PhoneOtpDelivery` adapter and additive OTP table. Keep existing
`VerificationDelivery.send({destination,purpose,token})` and43-character confirmation
contracts unchanged. Reusing `token` for numeric codes would break callers and
weaken the current global-token lookup; provider-managed verification would move
attempt/expiry semantics outside our transactional source of truth. Neither is
part of this slice. The new service owns code generation, verification, quotas and
contact updates; the provider adapter only dispatches a message.

## Public API

All routes require fresh active pending/approved identity. Rejected and revoked
sessions retain existing denial. Cookie mutations require CSRF/origin validation;
bearer sessions receive identical authorization. Responses are private `no-store`.

- `GET /v1/auth/verification/phone/capabilities` returns
  `{numericOtp:{available:boolean,reason:"available"|"disabled"|"unconfigured"},legacyToken:{available:true}}`.
  `available` describes server configuration, never provider health or actual
  delivery. It reveals no URL, credential presence details, sender, code or phone.
- `POST /v1/auth/verification/phone/otp` accepts strict `{phone:string}` in existing
  E.164 format and required `Idempotency-Key` matching existing core limits
  (8–100 characters, `[A-Za-z0-9_-]`). This is both initial request and resend.
  A new key creates a new challenge after cooldown/quota checks. Return201 with
  `{challengeId:string,expiresAt:string,resendAfter:string,delivery:"accepted"|"unavailable"|"unknown"}`.
  Dates are ISO UTC. The same authorized key/body returns the same challenge/result
  without a second dispatch or quota consumption; a changed body returns409.
- `POST /v1/auth/verification/phone/otp/confirm` accepts strict
  `{challengeId:UUID,code:string}`; code must match `^[0-9]{6}$`, including leading
  zeros. Return201 `{verified:true}` only after the phone transaction commits.
  Invalid, wrong-user, consumed, expired or exhausted challenge returns400 with
  bounded code `phone_otp_invalid` and no remaining-attempt count.

Disabled/unconfigured request returns503 `phone_otp_unavailable` before generating
a challenge, quota mutation or dispatch. Cooldown/quota rejects429
`phone_otp_rate_limited`, with integer `Retry-After` and response `retryAfterSeconds`;
do not disclose whether a destination belongs to another account. Existing ingress
limits still apply. Invalid body returns400. Existing claimed-phone uniqueness
conflict returns409 `phone_otp_contact_unavailable` without revealing another user.
No successful/error response or OpenAPI example exposes a generated code.

## Configuration and provider contract

New server-only names: `PHONE_OTP_ENABLED` (default `false`), `PHONE_OTP_PEPPER`,
`PHONE_OTP_GATEWAY_URL`, `PHONE_OTP_GATEWAY_TOKEN`. Existing verification gateway
configuration/production requirements remain unchanged. Availability requires
enabled=true and all three valid OTP bindings; missing bindings produce capability
`unconfigured` and endpoint503 without taking the whole application down. If a
binding is supplied but malformed, normal environment validation rejects it.

Pepper is an independently generated secret containing at least32 random bytes,
encoded as base64url and decoded before use. A rotation invalidates outstanding
five-minute OTPs and changes destination-quota digests. Disable new phone sends
for a full rolling hour before rotation so old destination events drain; otherwise
a rotation could reset cross-account destination limits. Never reuse the legacy
gateway token as pepper. Supply values
through secure environment settings; never request values in chat or embed them
in examples, logs, tests or Git. Tests use explicitly named test-only random bytes.

`PhoneOtpDelivery.send(message: PhoneOtpMessage): Promise<PhoneOtpDispatch>` uses:

```ts
type PhoneOtpMessage = {
  version: 1;
  challengeId: string;
  destination: string;
  code: string;
  expiresAt: string;
};
type PhoneOtpDispatch = 'accepted' | 'unavailable' | 'unknown';
```

POST the exact versioned body to a clean credential-free public HTTPS URL, port443,
with bearer OTP gateway token and `Idempotency-Key: challengeId`. Reuse the
repository's hardened outbound transport approach: reject redirects, private/
loopback/link-local DNS answers, and rebinding; keep TLS verification and bound
the whole request to five seconds. Bound acknowledgment reads to4KiB.
Only202 with strict `{version:1,challengeId,accepted:true}` matching the request
means `accepted`. Definite gateway rejection (4xx other than408) means
`unavailable`; network/timeout,408,5xx, malformed/mismatched acknowledgment or any
unexpected2xx means `unknown`, since dispatch may have happened. Do not attach
provider response/error text to public errors or logs. Do not automatically retry.

There is no nonproduction filesystem/code fallback in this adapter. Unit/integration
tests inject a captured adapter; production never exposes codes. Provider-specific
sender/template credentials live behind the gateway, not in the browser/API body.

## Storage, generation and quota semantics

Migration017 adds `phone_otp_challenges`: UUID id, user FK, destination text,
code_digest text, expires_at, attempts integer default0 constrained0–5, used_at,
invalidated_at, created_at, and dispatch_state (`pending|accepted|unavailable|unknown`).
Store expiry exactly five minutes from creation. Read clock_timestamp() after
acquiring locks for expiry/cooldown/quota decisions: transaction-start now() can
be stale after a lock wait and must not extend a code lifetime.
Add user/created index and destination digest/created send-event index.

Add `phone_otp_send_events(id UUID,user_id FK,destination_digest text,created_at)`
for exact rolling one-hour quotas. Codes/plaintext code material never enter either
table. Retain events for at least one hour; cleanup/retention jobs are deferred and
do not influence correctness because queries use timestamp predicates.

Generate `randomInt(0,1_000_000).toString().padStart(6,'0')`. Digest is HMAC-SHA256
using decoded pepper over UTF-8 JSON tuple
`["raui.phone-otp.v1",challengeId,userId,destination,code]`; compare fixed-length
decoded digests with `timingSafeEqual`. Destination quota keys use a separate
domain-tagged HMAC tuple `["raui.phone-otp.destination.v1",destination]`.
Plain SHA256 cannot protect the one-million-code space against an offline attack.

Request/resend uses one transaction to reauthorize current session/user, lock user,
take a destination advisory transaction lock keyed by its HMAC digest, then lock
affected challenges. Use this order everywhere: user -> destination lock when
requesting -> challenges. On any previous send by this user within60 seconds,
reject429. Permit at most five attempts to send within the previous hour per user
AND per destination across all users. The sixth is denied. Destination lock makes
cross-account requests obey one shared quota; user lock serializes own resends.

When numeric OTP is configured and enabled, share these user/destination send
limits with the legacy phone request path. Otherwise legacy phone delivery could
bypass the SMS budget. Reserve the legacy send event under the same locks before
its challenge allocation; preserve the existing token schema and add only the
bounded429 policy failure. Email/reset requests do not consume this quota.

Count quota when a challenge is allocated, including unavailable/unknown dispatch;
transaction failure before allocation commits consumes nothing. Successful
confirmation counts no new send. Idempotent replay counts no new send.
Request allocation invalidates every unused legacy `purpose='phone'` challenge and
every active OTP challenge for that user, then creates the new challenge/event.
Legacy phone request must also invalidate active OTPs under the same user lock.
Confirmation of either format locks user before its challenge and refuses invalidated
challenges. No old message may subsequently revert the verified destination.

## Dispatch idempotency and crash boundaries

Use the existing idempotency mechanism for durable challenge allocation, but never
perform network dispatch inside its DB transaction. Store the challenge allocation
response with `delivery:'unknown'`. After commit, atomically claim
`dispatch_state='pending'` by changing it to `unknown` before sending; only the
claiming request receives the plaintext code generated during allocation and
dispatches. Concurrent replay returns unknown while that request is in flight.
Update the stored challenge/idempotency response to the final bounded result in a
second transaction. The original response and all later replays then agree once
dispatch settles. On crash before dispatch, no code can be recovered from DB;
remain unknown until expiry/cooldown allows a new request. On crash after provider
acceptance, no blind resend occurs. Fresh identity authorization precedes every
replay. Do not store plaintext/encrypted code in the idempotency ledger.

Implementation must introduce a small OTP-specific allocation/dispatch wrapper
around the existing ledger rather than altering existing routes' replay semantics.
Use existing ledger uniqueness/advisory locking and response JSON fields; scope
`phone-otp-request`. When a transaction needs both the request-key advisory lock
and user row, always take request-key advisory lock -> user -> destination ->
challenge -> ledger. Allocation, replay, dispatch claim and final response updates
must follow that same order; never take the request-key lock after the user. A
post-commit dispatch claim must recheck active current identity and that the
challenge is still unused, unexpired and not invalidated, before claiming a send. Record request allocation and confirmation with bounded
challenge ID/user ID events; no code, digest, full phone, token or provider body in
audit/telemetry. Public API readiness remains independent of provider delivery.

## Confirmation and races

Lock active current user/session first, then that user's challenge by ID; validate
pending/approved approval state again under locks. Unknown/wrong-user IDs never
consume another user's attempts. A wrong code on an eligible owned challenge
increments attempts; fifth failure also invalidates the challenge. Return an
internal outcome from the transaction and throw HTTP400 only after COMMIT so the
counter cannot roll back. Expired/used/invalidated/exhausted challenges never succeed.

A matching code consumes the challenge and updates `users.phone` and
`phone_verified_at` atomically, invalidating other phone challenges under the same
user lock. Unique-phone conflict leaves the phone unchanged, invalidates this
challenge in a committed error outcome, and yields generic409. Put the phone
UPDATE behind a SAVEPOINT: PostgreSQL uniqueness errors abort the transaction;
ROLLBACK TO the savepoint before invalidating the challenge and committing the
error outcome. Acquire user/challenge locks before the savepoint so rollback does
not release the serialization locks. Approval state,
role, email verification and activation are unchanged. Session revocation or
deactivation serialized before confirmation prevents its update. Concurrent
correct submissions produce one confirmation audit and one success, then400.

## Client behavior

The profile fetches capability alongside own profile with existing identity/unmount
guards. Default disabled state keeps the current long-token form explicitly labeled
as such; do not replace its input silently. When numericOtp.available, offer a
separate SMS-code form, show E.164 input, request/resend button, six-digit text input
(`inputMode="numeric"`, `autoComplete="one-time-code"`, `maxLength=6`), and confirm.
Never use number input, which loses leading zeros. Store challenge ID/timing only
in component state, not URL/localStorage. Clear code after submission and all OTP
state on identity change/unmount; discard late capability/request/confirm results.

Use exact copy: accepted “Запрос на отправку SMS принят. Доставка не подтверждена.”;
unknown “Не удалось подтвердить отправку. Если SMS придёт, используйте код.”;
unavailable “SMS сейчас недоступно. Повторите запрос позже.”; disabled/unconfigured
“Подтверждение коротким кодом пока недоступно.” Confirmation refreshes authoritative
profile and shows contact verified only when its timestamp is present. Pending
registration remains pending. Cooldown countdown is advisory; server enforces limits.
