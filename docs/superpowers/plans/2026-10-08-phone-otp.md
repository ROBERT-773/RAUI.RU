# Authenticated Phone OTP Implementation Plan

> For agentic workers: use superpowers:subagent-driven-development or
> superpowers:executing-plans according to the user's preserved execution method.
> The user selected parallel agents and autonomous continuation. This artifact is

> authorized continuation. Runtime work has not started, and no deployment is authorized.

**Goal:** Active pending/approved users verify their own phone using bounded numeric
codes while preserving legacy verification and independent staff registration approval.

**Architecture:** New OTP service/table/adapter; transactional allocation and
attempts; post-commit single dispatch; authenticated capability contract and separate
profile UI. No anonymous auth or provider-managed verification.

**Tech stack:** Node24, pnpm10, strict TypeScript, NestJS, PostgreSQL, Next.js/React.

**Spec:** [2026-10-08-phone-otp.md](../specs/2026-10-08-phone-otp.md).

## Global constraints

- Existing checkout, feature branch; immutable migrations001–016. No real dispatch,
  merge or deployment; provider secrets only through secure environment settings.
- Six digits; five minutes; five failed attempts;60-second account cooldown;
  five sends/rolling hour per account AND destination; required request idempotency.
- Server-pepper HMAC binds challenge/user/destination/code; no code material in DB,
  logs, API responses or browser persistent storage. No local-code fallback.
- User -> destination advisory lock on requests -> challenge locking. Wrong attempts
  and generic phone conflicts commit before HTTP error. Legacy/OTP cross-invalidate.
- Disabled by default; unconfigured request503; capability safe boolean/reason;
  provider acceptance is not delivery. Legacy gateway payload/43-character tokens stay.
- OTP does not approve registrations, mutate roles/activation or reset passwords.

## Review focus

1. Wrong-code errors must leave persisted attempts; rolling-back exceptions must
   never restore the five guesses (Task3 PG assertion).
2. Two accounts requesting the same number must share quota and never confirm one
   another's challenge (Task3 parallel HTTP assertion).
3. Lost acknowledgment/crash must not cause replay to send twice or retain code
   material in the ledger (Tasks2–3 captured adapter and DB assertions).
4. A delayed legacy/OTP message must not restore an old phone after resend/change
   (Task3 cross-format HTTP tests).
5. Changing identity while a request finishes must not expose an old challenge/code
   or imply staff approval (Task4 deferred-component tests).
