# Безопасные миграции

## 043 — одноразовые коды входа по почте

`043_email_sign_in.sql` добавляет таблицы `email_sign_in_challenges` и `email_sign_in_failures`. Действующим пользователям сохраняются пароль, подтверждённые контакты, роль и сессии. Триггер погашает ранее выданные коды пользователя при смене его почты, подтверждения почты, пароля, активности, роли или решения о допуске.

Для включения нужны `EMAIL_SIGN_IN_ENABLED=true`, отдельный серверный ключ `EMAIL_SIGN_IN_PEPPER` (минимум 32 случайных байта, base64url) и настроенное восстановление через SMTP с HTTPS-адресом портала. Шлюз получает письмо с шестизначным кодом. Код действует час. Новый запрос в том же браузере заменяет предыдущий код, для повторной отправки нужна минута. На адрес разрешены пять отправок и пять неверных попыток за скользящий час. Повтор с тем же ключом запроса возвращает прежнюю квитанцию. Общий ответ сообщает, когда можно повторить запрос.

При откате отключите `EMAIL_SIGN_IN_ENABLED` и верните предыдущий образ приложения. Сохраните таблицы, триггер и созданные кабинеты. Чтобы перед повторным включением погасить все прежние коды, замените `EMAIL_SIGN_IN_PEPPER` и выдержите час для истечения прежних почасовых ограничений.

## 042 — фото агента и логотип агентства

`042_professional_profile_image.sql` добавляет в `public_professional_profiles` поле `image_id`. У всех прежних профилей оно пустое. Файлы WebP хранятся в приватном хранилище объектов. При замене изображения или удалении ссылки на него триггер в той же транзакции ставит прежний файл в очередь `professional_photo_cleanup`. Если хранилище временно недоступно, действующий обработчик очереди повторит удаление.

При откате приложения сохраните поле `image_id`, триггер, очередь и используемые файлы. Прежнее приложение работает с расширенной схемой, а прежний обработчик продолжает разбирать очередь. После возврата версии с поддержкой изображений выбранные фото и логотипы снова станут доступны в профилях.

## 041 — предложения по работе портала

`041_portal_feedback.sql` создаёт пустую таблицу предложений пользователей. Уникальная пара автора и идентификатора отправки защищает от дублей при повторе. Индекс по дате и ID поддерживает просмотр от новых предложений к старым. В базе хранится ссылка на аккаунт, а администратор видит его публичный ID.

Прежнее приложение совместимо со схемой 041. При откате приложения сохраните таблицу вместе с уже поступившими предложениями. После возврата версии с разделом обратной связи администратор снова увидит их.

## 040 — способы связи продавца

`040_seller_contact_settings.sql` добавляет режим связи в профиль, подтверждённые номера продавца, выбор номеров для каждого объявления и отдельные одноразовые коды для подтверждения дополнительных телефонов. Прежние объявления сохраняют режим переписки. Подтверждённый номер аккаунта становится доступен для выбора в кабинете. Связь с конкретным объявлением появляется только после явного выбора автора.

При откате интерфейса сохраните таблицы и их данные. Для объявлений с режимом «Только звонки» сервер должен продолжать проверять запрет на начало диалога из карточки. Если потребуется вернуть прежний сервер, закройте создание обращений из карточек до восстановления этой проверки. Исправления схемы поставляются следующей миграцией.

Из корня: `pnpm build`, затем `pnpm db:migrate`. Автоматической schema sync
при старте API нет. Runner читает SQL из `apps/api/migrations` в фиксированном
порядке, проверяет SHA-256 ранее применённых файлов, serializes runners через
advisory lock и выполняет каждую миграцию в отдельной транзакции.
Lock timeout 5s, statement timeout 60s. Ошибка откатывает текущий файл полностью.
Применённые SQL менять нельзя: новые изменения — новый migration file.

001 — expand-only: новые таблицы/индексы/constraints, category seeds,
PostGIS extension и append-only audit/history triggers. Foundation tables/data
не изменяются. Extension может потребовать отдельный привилегированный
migration user; runtime DB account должен иметь только нужные DML-права.
Локальный Compose user имеет права для extension/CREATEDB тестов; это не
образец production ACL.

Индексы соответствуют текущим запросам: session token (unique) и user revoke;
membership by user; property owner/org; listing owner/org; listing history;
audit entity/id; pending moderation (unique); queue claim by available_at;
addresses GiST для будущих геозапросов. Search indexes/partitioning не добавлялись.

Rollback приложения: остановить media worker и вернуть previous API artifact;
оставить новые таблицы/данные, старый Foundation ими не пользуется. Запрещено
автоматически DROP новых таблиц после появления данных. Forward-fix — отдельная
миграция по expand → backfill → switch → contract; backfill отдельно от длинных
locking schema operations. Перед production migrations нужны backup/restore
и review конкретного deployment; этот этап ничего в production не применяет.

Тесты проверяют clean apply, repeatability, checksum mismatch и rollback
неудачной миграции. Integration runner создаёт отдельную local DB и удаляет
только её. `pnpm infra:down` сохраняет volume; не используйте `down -v` для
обычного сброса приложения. Audit/history удаления намеренно запрещены даже
локально: для тестов используются изолированные базы.

Phase 3 adds expand-only `002_search_product.sql`; see [search/product rollout](PHASE_3_SEARCH_PRODUCT.md). Migration 001 remains immutable. Integration suites use separate temporary databases and verify repeat execution.
